### Why not tool approval for a commit

Teams and Copilot Chat deliver **text**; the platform bridge turns the reader's `confirm` into the next Responses call's input text. MAF's approval is a
structured `function_approval_response` Content tied to a tool call **the model made**, so using it for `*_commit` would (1) put the commit in the model's tool set,
weakening "writes are only prepared by the model" to "...and approved", and (2) need a structured reply the channel cannot send. A Workflow's `request_info` /
`@response_handler` carries the same pause and resume, with the reply produced by **our code** after the exact-word, same-person, in-time check. `approval_mode`
is still the right primitive for a future read-only tool that must never run unattended; none exists today.

## 4. A FunctionTool from a catalog schema (d)

The catalog's `CapabilitySpec` carries `name`, `description`, `kind`, `needs_client`, `needs_year`, `schema`, `sensitive`, `implemented`, `chat_intent`, `tags`.
This code was run (from `backend/`, using the real `client_eligibility` spec and a fake gateway). It builds the tool once and carries the person per request:

```python
import json
from agent_framework import FunctionInvocationContext, FunctionTool
from application.capabilities import catalog

def tool_for(spec: catalog.CapabilitySpec, gateway) -> FunctionTool:
    async def forward(ctx: FunctionInvocationContext, **args):
        reply = await gateway.call_tool(ctx.kwargs["acting"], spec.name, args)   # forwards, computes nothing
        return json.dumps(reply.body)
    return FunctionTool(name=spec.name, description=spec.description, func=forward, input_model=spec.schema)

# per request:  await agent.run(question, function_invocation_kwargs={"acting": who})
```

Observed output:

```text
name matches: True
description matches: True
schema equal to catalog: True            # tool.parameters() == spec.schema
invoke -> body saw: {'client_id': 1001, 'tax_year': 2023, 'method': 'min_max'}
final: done | gateway saw: [('person-oid-1', 'client_eligibility', {'client_id': 4242, 'tax_year': 2023})]
```

The last line ran a real `Agent` with a scripted chat client: the model asked for `client_id=1`, a `FunctionMiddleware` overwrote it with `4242` (the reader's client),
and the body received the identity from `function_invocation_kwargs`. Cautions for RM-07 and RM-08:

1. **A mapping schema is not validated like a Pydantic model.** The docstring: a dict is "checked only for top-level `required` fields, `additionalProperties: false`, and
   property `enum` and primitive `type` values ... never rely on them as an authorization or security boundary." Observed: `tax_year="abc"` raised `_FunctionArgumentValidationError` (type), but nested constraints and `oneOf` are not enforced. The catalog's strict `jsonschema` check
   (today `first_schema_problem`) must stay as a middleware step.
2. `invoke` returns `list[Content]`; use `result_parser=` (or a middleware) to control the string the model sees.
3. `max_invocations` counts over the **tool instance's lifetime**, not per request: do not use it for the turn budget.
4. The model-facing schema is the catalog schema **minus** what the reader owns (`client_id`, year keys, what-if sizes) with `additionalProperties: true`
   (`toolset.offered_schema`). That projection is hard-coded in the orchestrator today (`CLIENT_PLACEHOLDER`, `YEAR_KEYS`, `SCENARIO_NUMBERS`, `_NOT_FOR_MODELS`). For "the catalog is the only source" it must become catalog metadata (finding F-07).

## 5. Spikes run (evidence for the verdicts)

**Workflow with a confirmation (RM-10b).** On core 1.24.0 a `Workflow` of three executors (prepare → confirm → commit) was built with
`WorkflowBuilder(start_executor=..., checkpoint_storage=InMemoryCheckpointStorage(), name="write").add_edge(...).build()`. `await wf.run("...")` ended in
`IDLE_WITH_PENDING_REQUESTS` with one `request_info` event (`Preview`) and no output; a checkpoint existed. A **freshly built** second graph then ran
`await wf2.run(responses={request_id: Decision(True)}, checkpoint_id=...)` and ended `IDLE` with the commit executor's output. So the pause, the typed reply and the
resume on a rebuilt graph work, which is what a restarted replica would do.

**MCP SDK per-request identity (RM-14).** `mcp.server.lowlevel.Server(..., on_call_tool=...)` served through `streamable_http_app(json_response=True)` and driven in process
with `httpx.ASGITransport`: the handler read `ctx.request.headers["x-test-user"]` and `["authorization"]` of **that** request in `stateless_http=True` (two users, two values)
and in stateful mode (initialize, then two calls with different users on one session). In stateful mode a second user presented the first user's `Mcp-Session-Id` and was served:
**the SDK does not bind a session to a person**, which the facade does (a foreign session is "unknown", D-65).

## Hosting: go / no-go and when to re-check

**Verdict (RM-12, D-128): NO-GO. The current host stays, behind the `main.py` seam.** Nothing in `channel_orchestrator`'s hosting changed in RM-12; what changed is that the seam is now provable and the Teams-silencing regression has a guard.

| Why not now | Evidence |
| --- | --- |
| Only pre-release builds exist | `pip index versions agent-framework-foundry-hosting` (2026-11-04): 29 releases, every one `a` or `b`, newest `1.0.0b261030`; without `--pre`, `pip install` finds no matching distribution. A production build installs no pre-release (D-76). |
| No Activity handler | The package, `azure-ai-agentserver-core` 2.3.0, `-responses` 2.4.0 and `-invocations` 1.3.0 serve `Responses` and `Invocations` only (section 3). Teams does not need the container to serve `activity`, but the brief's literal rule is "hosting if it supports Activity". |
| Per-request identity under hosting is unproven | An `Agent`'s tools are built from a zero-argument factory that cannot see the request; our identity reads `ResponseContext.client_headers`, the platform context and `x-agent-user-id` (`app/host.py`). A workflow factory receives the request; an agent factory does not (section 3). |
| Durable stores are not wanted | Hosting defaults to Foundry-backed session, checkpoint and approval stores; our state, including the single-use confirmation token, is in memory by decision (D-81). |

**What proves the seam** (`backend/tests/channel_orchestrator/test_orch_hosting_seam.py`, plus the older rules in `test_orch_structure.py`):

- Only `channel_orchestrator/app/main.py` imports a hosting package (`azure.ai.agentserver*` or `agent_framework_foundry_hosting`), across the orchestrator, the backend and `scripts/`.
- The zip-root `main.py` imports only `app.main`; `app/main.py` registers exactly one Responses handler, reaches the orchestrator only through `app.host` and `app.wiring`, stays at or under 60 lines and does not touch the agent framework.
- The agent framework is imported only by `app/core/maf_*.py`.
- The beta hosting package is not in either requirements file, no `--pre` is used, and the stable `azure-ai-agentserver-responses` is pinned; `azure.yaml`'s `entryPoint` and the Dockerfile's `CMD` both start `main.py`.
- **The Teams-silencing guard (D-100).** `azure.yaml`'s container `protocols:` must be exactly `responses`, and the agent endpoint's `protocols:` must contain both `activity` and `responses`. `activity` on the container makes the platform post Teams messages to `/activity/messages`, which the container does not serve (404, no error shown in Teams). The test reads the file with a small indentation walker (no YAML dependency) and has a crafted failing input for each way to break it.

**Re-check conditions.** Propose a swap only when all of these hold:

1. `agent-framework-foundry-hosting` is generally available: `pip index versions agent-framework-foundry-hosting` (no `--pre`) lists a `1.x` release without an `a`, `b` or `rc` suffix, and its `agent-framework-core` range admits the version the orchestrator pins.
2. Activity is settled. Either the package, or the platform's *Hosted agent runtime contract*, documents an Activity handler for the container (and then `azure.yaml` could declare `activity` there, which `test_orch_hosting_seam.py` would have to be changed to allow, deliberately), or the Responses-only container with `activity` declared on the endpoint is confirmed as the supported Teams path. Either way, state which.
3. Per-request identity works. A spike shows that `get_request_context()` (`user_id`, `original_subject`) and `ResponseContext.client_headers` reach `app/host.py`'s identity resolution so the same `ActingIdentity`, or the same refusal, comes out for each configured identity source (`original-subject`, `platform`, `agent-user-id`), and that the identity reaches the tools (through a workflow factory, or `function_invocation_kwargs`).
4. State is acceptable. Hosting's Foundry-backed stores either work from this tenant's network or are switched off; the prepared write's token is never persisted (D-81).

**What to run at the swap**, in order: the seam test (change `SEAM` only if the file is renamed); `azure.yaml` unchanged (container `responses`, endpoint `activity` and `responses`); the whole orchestrator suite and goldens unchanged; `python frontend/tools/check_all.py`; then live, with the previous agent version recorded for rollback, a real Teams message round trip and `GET /agents/<name>` showing `definition.protocol_versions` is `responses` only (the runbook's invariants).

**Owner decision.** None is needed now. Revisit when the hosting package reaches GA or when the platform documents an Activity protocol for containers.
