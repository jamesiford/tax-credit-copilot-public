# Changelog

All notable changes to this project are recorded here, so changes can be followed without reading git history. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org/) once it is released.

**How to use this file**

- Add an entry under `## [Unreleased]` in the same commit as the change. One line per change, in plain language.
- Use the groups `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed` and `Security`.
- Say what an operator has to do: new setting names and defaults, migrations to run, behaviour that now differs.
- Keep entries customer-neutral. This is a public repository: no customer names, hostnames or identifiers.
- Never rewrite or delete an earlier entry. If one was wrong, add a correcting entry.
- When a release is cut, rename `Unreleased` to the version and date, and start a new `Unreleased` section.

## [Unreleased]

### Added
- Proof that a program is added by data: a test registers a fictional program (`ZZ_DEMO_JTC`, every value invented and flagged, never law) through a temporary rules folder and registry with synthetic payroll for a made-up state, and shows it listed as calculable for its authored years, assessed and calculated by the unchanged engine, with a program that has no authored year declined by name. No source file changed. Test-only; operators need do nothing.
- Run requests no longer assume Georgia. `POST /api/v2/clients/{id}/runs` and the base-year route accept an omitted `state`: it is derived from the states the client's payroll holds, narrowed to programs with an authored year pack (registry order), and a location's base year takes its state and program from the location. A caller that sends `state` is unchanged. If nothing can be derived the old `"GA"` default still applies as a **deprecated fallback** that logs a warning and raises a `DeprecationWarning`: pass `state` explicitly to silence it. Read endpoints keep their existing `state` defaults.
- Two operator scripts: `scripts/validate-rule-pack.py <path|--all> [--json]` (exit 0 valid, 1 errors, 2 usage) and `scripts/new-program.py program|year` (a draft registry entry and base-pack skeleton, or a `<year>.draft.json` year skeleton the engine ignores; every statutory value is `null` and flagged, so it fails validation until a person fills it from a cited source). Neither verifies or activates anything.
- Rule packs now have a JSON Schema (`backend/rules/schema/rule-pack.schema.json`, `schema_version` 1, for base packs and year packs) and a semantic validator (`backend/tools/pack_validation.py`): pack version format, file and jurisdiction naming, unique credit codes across the registry, supported models only (a percentage-of-wages benefit is reported, not silently priced), `thresholds_by_year` consistency, no inheritance between years and a `_verified` claim only with no outstanding `_prototype_verify` flag. A pass means well-formed, not verified. All ten shipped packs validate; one (a percentage-of-wages describable pack) carries a warning. Operators need do nothing.
- Program registry: programs are now data. `backend/rules/registry/programs.json` lists every program (code, state, pack file, jurisdiction, supported models, stored lifecycle; `calculable` is derived from authored year packs, never typed), federal programs included. `STATE_TO_PACK` and `PROGRAM_CODE_TO_PACK` keep their names and contents and are now views over it, so nothing observable changes. New optional settings `RULES_DIR` and `PROGRAM_REGISTRY_FILE` (defaults: the packaged folder) let a deployment read packs from elsewhere. Operators need do nothing.
- Teams and Copilot Cowork: **run batches** from chat. New capabilities `run_batch_prepare` / `run_batch_commit` (a two-step write: the preview is the dry run, above `RUN_BATCH_CONFIRM_ABOVE` runs it refuses until the person confirms the count and the agent prepares again with `confirm_items`), `run_batch_status` and `run_batch_list`. The commit is authored by the person, only listed writers may start one, and every account a request names is authorized. The catalog now offers 36 tools, so the gateway tool list changes and the orchestrator and the Cowork plugin must be republished (`python scripts/vendor-orchestrator.py`, `azd deploy` in `channel_orchestrator`, `python scripts/build-cowork-plugin.py`); the Cowork skill `tcc-figures-and-writes` now says when to offer a batch run and always to preview first. Existing tools are unchanged.
- A request that names clients in a list (`client_ids`, `scope.client_ids`, `account_ids`) now has every one of them checked by the client authorizer at the API edge and at the capability edge, not only a single `client_id`.
- Portal: **Runs**. In the portfolio, select clients with the new checkboxes ("select all on this page", and "select all matching" when the filters can be handed to the server), then **Run for N clients**: a start dialog always shows the dry-run preview first (clients and years in scope, last runs, unavailable clients with the reason, and "up to N may be skipped if unchanged" as an upper bound that is decided when each run starts, never a promise), asks for the item count to be typed above `RUN_BATCH_CONFIRM_ABOVE`, and sends an idempotency key so a double click queues one batch. The new **Runs** page (`/runs`, `/runs/<batch id>`, under "What needs a decision") shows batches, progress, items, failures grouped by cause with the remedy, **Cancel** and **Retry failed**, and a degraded `run_worker` banner; it polls with backoff, stops when the batch finishes and pauses while the tab is hidden. Optional, off by default: set `VITE_RUN_AS_BATCH=true` when building (or `localStorage['tcc.run-as-batch']='1'` in one browser) and Run assessment, Assess and Run TY... now queue a one-client batch and open its progress instead of blocking.

Applied to the Delta paths and to every SQL statement in `source_sql.py`. A later release replaces these with the full data-model mapping.
- **A declarative source mapping** (`backend/data/source/mapping/`: typed model, `default.json`, one resolver). Renaming a table or column, adding a prefix, changing case, or adding or dropping an unused field is a file change: the Delta reader and writer, the SQL fast path (`source_queries.py`), the governed data-query model, the tenant allow-list and the grants all resolve names through it. `SOURCE_MAPPING_FILE` layers a file over the default; `SOURCE_TABLE_*` remain overrides. Column case is resolved from the table's own schema at first read, so `Accountid` and `AccountId` both work.
- `scripts/validate-source-schema.py` (and a boot check, `SOURCE_SCHEMA_VALIDATION`, default `warn`) compares the mapping with the lake and reports required fields missing, optional ones absent, re-cased, re-typed and extra columns; `--print-effective` prints the mapping in force. `/api/ready` reports the boot verdict under `source_schema`.
- Named transforms `worksite_location` and `null_pay_date` (`WORKSITE_LOCATION_SOURCE`, `NULL_PAY_DATE_POLICY`). The SQL aggregates apply the same policy. Design: `docs/architecture/SOURCE-MAPPING.md`.
- **App-owned lookups** (`backend/data/lookups/`): `PayCodeCategory`, `EntityFiscalYearRules`, `PayFrequency` and `IndustryType` are not in the schema the customer shared, and are never authored in their lakehouse. One resolver reads them in provider order `source -> override -> seed -> default -> none` with a per-lookup `strict`/`assume` policy; every answer carries its provider, version and `inferred` flag. The override layer is `tcc_ops.lookup_override`/`lookup_audit` (migration 0003; SQLite for local runs, the Warehouse when deployed; `LOOKUP_STORE`), authored with `scripts/lookups.py list|show|import|export|diff|audit`. Seeds are versioned files in `backend/rules/lookups/`. See `docs/architecture/APP-OWNED-LOOKUPS.md`.
- **Unmapped pay codes are never silent.** Pay-code inclusion (the hardcoded 8-name map in `to_bcs.py`, now a seed) resolves per account through override then seed. The projection controls report distinct unmapped codes and rows; each row is flagged (`_Pay_Code_Unmapped`, `_Pay_Code_Defaulted`). Under `strict` (the default for customer-classified data, where the seed is not trusted) an unmapped code blocks the calculation with a message listing the codes; under `assume` it passes through flagged.
- `fiscal_window_for_state_year` returns the window with its provenance and `assumed` flag (it used to return bare dates and swallow every exception); the assessment carries it on each claim cell as `fiscal_window`. A fiscal rule can come from an app-owned override; `FISCAL_RULES_POLICY=strict` blocks instead of assuming a calendar year.

- `scripts/fabric/build-sample-lakehouse.py` builds the sample lakehouse in the source mapping's shape (table names, column names and case, types including `int32`, the tenant partition) from the sample data or the scale generator, to local disk or the Fabric lakehouse (`--fabric --yes`), reconciling row counts and checksums before and after; `--dry-run` writes nothing; the app-owned lookups are written only with `--with-lookups`. `scripts/generate-synthetic-source.py` generates N accounts / M rows with a realistic skew, deterministic by seed (`data/source/scale.py`, `data/source/build_lake.py`).

- **Source reads scale with the account, not the table** (`docs/architecture/SCALE-READS.md`). `Address`, `StateCountyZip`, `Employment` and `EntityFiscalYearRules` are read by the keys one account references (a range filter on the key, then a semi-join in Arrow), never in full; only the columns the engine's path needs are read (`"engine": false` in the source mapping marks the rest); an unknown account id is found out from the tiny `Account` read and remembered instead of re-reading every table each time. On a synthetic lake a small account now reads about a tenth of the rows and a fifth of the bytes it did, and a repeated unknown id reads nothing.
- The per-account dataset cache is **bounded** (`SOURCE_CACHE_MB`, `SOURCE_CACHE_ACCOUNTS`, least recently used first), keyed by account and the Payroll Delta version (`SOURCE_VERSION_CHECK_SECONDS`) so a reloaded lake is noticed and only the changed account is read again, shares one read between concurrent requests (single-flight), and refuses an enormous account (`SOURCE_MAX_ACCOUNT_ROWS`, typed `AccountTooLarge`) before loading it.
- Every source read and cache decision is counted (`data/source/read_stats.py`), reported under `/api/ready` `source_schema.reads`; a regression test fails if a Delta table is read anywhere but the one filtered, projected scan. `scripts/fabric/benchmark-source-reads.py` measures time, memory and bytes read.
- The portfolio page reads every client's engagement scopes in a few batched reads instead of one per client.
- Optional **Silver** table (`scripts/fabric/build-silver.py`, `SOURCE_SILVER=off|auto|require`, default `off`): engine-shaped payroll partitioned by account, built once and refreshed by source version. The pay-code lookup is applied at read time. A test proves its rows and the assessment equal the raw path's.
- `docs/data/SOURCE-LAYOUT-GUIDANCE.md`: layout recommendations for the customer's lakehouse (recommended, not applied).

### Changed
- **More of the product stops assuming Georgia.** Location-level reads (unit rebase, unit and employee what-ifs), the employee drill, and the channel capabilities that take a client (`client_eligibility`, `client_at_risk`, `calc_walkthrough`, `employee_drill`, `simulate`) now derive the state from the location, the client's payroll and the registry when `state` is omitted, instead of defaulting to `GA` (the catalog no longer carries a `state` default, so republish the orchestrator and the Cowork plugin). The synchronous run endpoint already returns `state` and `program_code`; the choice is now also logged. A client with payroll only in Georgia is unchanged. Georgia-only surfaces (rules ingestion, the ingestion views, demo simulators) keep their defaults by design.
- **A Gold write that does not validate is retried once, then stays failed.** When the section 9 check after a run finds a mixed current state, or the writer fails, the batch item is marked failed with the named cause `gold_write` and a remedy, its lease is released, and it is retried once with no other worker holding the client. A second failure stays failed and visible in the batch; it is never counted as a success.
- **`RUN_WORKER_CONCURRENCY` now defaults to `1`** (and so do the Terraform `run_worker_concurrency` variable and the worker module), until concurrent Gold writes are measured on a live Warehouse. Raise it (maximum 8) only while watching the Warehouse write-conflict retry counts (errors 24556, 3960, 1205); set it explicitly if you relied on the previous default of 2.
- **Batch planning is program-aware.** A batch now queues one item per (client, program): a client with payroll in several states that each have a calculable program is run for each (the set comes from the client book's footprint and the registry, with no payroll scan), and a named `program_code` applies to everyone. The preview lists `programs` (items per program), `program_items` and `multi_program_clients`; items carry their program. Today only Georgia is calculable, so existing batches are unchanged.
- **Run batches no longer skip unchanged clients by default.** A new `skip_unchanged` option (API, command, planner, channel `options.skip_unchanged`, and an unchecked "Skip clients whose data and rules are unchanged" box in the start dialog) turns skipping on; `force` is still accepted and wins. A run now records a client-wide data fingerprint (a digest of all the client's payroll inside any authored year's fiscal window) in the manifest's `source_snapshot_id`, and a skip needs it to match along with the assumption hashes and rule pack version, so a restated prior year is caught. A manifest without it means "cannot tell, so run": the first batch after upgrading cannot skip anything. The preview reports `skip_coverage` (`all_years`, `cannot_tell_yet`) and still only an upper bound. Channel tool schemas changed (an options field): republish the orchestrator and the Cowork plugin.
- The lakehouse SQL aggregate reads (client scope, client book, fiscal windows) connect through `LakehouseSqlConnection` and the lakehouse settings, never the Warehouse connection, so the two may be on different hosts.

- The pay frequency label (`Pay_Frequency`) is derived from the measured period span, never from the source's surrogate id (kept as `_Source_Pay_Frequency_Id`); the `PayFrequency` lookup is no longer needed. The industry label comes from a versioned, `inferred` seed.
- **No client is known to the code.** The client list, default selection, warm-up and every "first client" read come from what the source lists. `DEFAULT_FLEX_ACCOUNT_ID` (1001) and `configured_account_id()` are gone: a single-tenant fixture source declares its account in `FIXTURE_ACCOUNT_ID` (replacing `FLEX_ACCOUNT_ID`, no default), and a read that names no tenant on the lakehouse returns nothing rather than another client's rows. Warm-up pre-reads the first `TCC_WARM_CLIENTS` (3) accounts and warms the sealed reference run only where `REFERENCE_ACCOUNT_ID` is set.
- The certified reference run is optional and identified only by `REFERENCE_ACCOUNT_ID` (unset by default). Without it the sealed reference views answer 503 `reference_dataset` with the remedy; every other screen is unaffected. Operator checks (`check_certified_live`, `verify_gold_reads`, `verify_unit_filter`) read the same setting.
- `synthetic` on a client now comes from an `IsSynthetic` marker on the account or from `DATA_CLASSIFICATION=synthetic`, never from an id range (`>= 2000`). The invented tier-1 designation for generated Georgia locations applies only in a `synthetic` environment; elsewhere a location with no recorded designation is unassigned and the pack threshold applies (no figure moves: tier 1's minimum equals the pack's).
- The illustrative claim seed refuses unless `DATA_CLASSIFICATION=synthetic` and `TCC_ALLOW_SEED=1`, only writes to an account whose name is the expected seed name, and the provisioning hook sets the flag only for a synthetic environment.
- The guided tour is built from the loaded book by role (largest identified credit, on the line, declining) and omits a role nobody plays. The scripted reference-data walk is `lib/demoTour.js`, loaded only when `VITE_DEMO_TOUR` is set. `channel-live-smoke.py` takes or discovers its clients.
- A guard test fails if production code (backend or frontend) names a demo client id or name, or tells demo from real by an id threshold.
- **Unavailable is no longer shown as "not assessed".** When the claim store (or one client's engagement scope) cannot be read, `GET /api/v2/portfolio` still answers `200` with the `degraded` list, but each affected row now carries `data_unavailable: true`, the dependency (`unavailable_dependency`), the band `unavailable`, and null status, outcome and figures, instead of the "not assessed" status. `assessed_clients` and `unassessed_clients` are `null` (not `0`) when the whole store could not be read, and a new `unavailable_clients` count is always present. Unavailable rows sort after the ranked rows, appear in every filtered view, and the page, the chat (`book_rank`) and the page summary say "unavailable" and never imply a client was assessed with no result. An empty claims table is unchanged: every client is still "not assessed". Status stays `200`: a `503` would take the whole book off the screen for one failing dependency. **Operators:** read the banner's remedy; API clients should treat `data_unavailable` rows as unknown, not as "nothing to do".
- **Silent fallbacks removed.** A client's fiscal rules no longer fall from a failing SQL read to the ten-table Delta load (every payroll row, about 132 s cold at demo size); a failure is logged and the window is the flagged calendar-year assumption, unless `SOURCE_FALLBACK=delta` is set (then a bounded read of `Entity` and `EntityFiscalYearRules`). The client book, the payroll footprint and the rule-pack reader no longer swallow every exception: an outage is a typed failure reported as `degraded`, and a bug in our own code now propagates instead of being shown as an empty page. A failed footprint scan is not retried for 60 seconds. An unconfigured lakehouse source is now reported as `source_lakehouse` degraded rather than as an empty client book. **Operators:** read the `degraded` list or the banner; nothing is read from another store for claims, engagements, findings or manifests.
- `backend/.env.example` is rewritten in sections, with every address-like placeholder commented out so leaving it cannot cause a connection attempt.
- The portal now opens when the certified reference run is not available (the source holds no reference client, account 1001, or the run cannot be built). `GET /api/workspace` and `POST /api/workspace/refresh` answer `200` with `available: false`, the reason and the remedy instead of an error, and the three views tied to the sealed run (Audit trail, Back-test, Calculations) say so; every other view reads the data that is present. A source that is not configured at all is still a `503` naming the settings to set.
- A source lakehouse that lacks the `PayFrequency`, `EntityFiscalYearRules` or `Employment` tables now loads: an absent optional table is read as "no rows", logged once with its consequence, and recorded on the dataset (`missing_tables`). A missing `EntityFiscalYearRules` keeps the flagged calendar-year assumption for the fiscal window; a missing `PayCode` table is still an error; a table that exists but cannot be read still raises.
- A blank or unset `DATA_SOURCE` now resolves to `lakehouse` everywhere (the reference workspace used to treat blank as the local CSV fixture and failed with "Reference workspace inputs missing"). Set `DATA_SOURCE=csv` explicitly for the local test fixture. If the source is the lakehouse but `FABRIC_WORKSPACE` and `FABRIC_LAKEHOUSE` are not set, the API now answers `503` with a body naming the dependency and the settings to set (typed error `SourceNotConfigured`).
- `SOURCE_SCHEMA` may now be set to an empty value, meaning a lakehouse that is not schema-enabled (`Tables/<table>`, and `[lakehouse]..[table]` in SQL). **A `SOURCE_SCHEMA=` line that is present but blank used to mean the default `tcc_source`; it now means no schema.** Remove the line (or set the name) if you want the default.
- With `ENVIRONMENT=local` (the default) the Azure credential no longer includes the managed-identity probe, which removes the long wait on a developer machine. Deployed behaviour (managed identity selected by `AZURE_CLIENT_ID`) is unchanged. To restore the probe locally set `AZURE_TOKEN_CREDENTIALS=managedidentitycredential`.
