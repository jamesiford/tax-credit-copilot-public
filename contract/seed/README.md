# Seed: the starting state of each profile, as data

A different implementation loads this to start from the same state the recordings were taken from. Generated by
`python -m contract.seed_export --profile P1|P2`; `manifest.json` in each profile lists every file with its row count, column list and SHA-256.
Files are `*.jsonl.gz` (gzip, mtime 0, UTF-8 JSON Lines, one object per row, keys in column order). Values are exactly as stored by the
harness's SQLite stores: money is a JSON number (SQLite stores the engine's whole-dollar money as a float), dates are ISO text, bit columns are 0/1.

| **P1** | `DATA_SOURCE=csv`, the committed synthetic pay-period file, account 1001; one engine run, TY2025 (the run writes every authored year) | 11 | 18,111 |
| **P2** | a local Delta lakehouse of the four synthetic clients (2001-2004), engine run per client | 20 | 390,660 |
| **G1 / G1L** | P1 + Entra sign-in + the channel gateway in front of the API (G1L: gateway limit 6/min). Same seed as P1; no extra data. | (P1) | |

## Load order

1. `source/*`: P1: the pay-period file as the CSV source (`DATA_SOURCE=csv`, account 1001); P2: the lakehouse tables. A port reading SQL Server loads them into its source schema (the customer-neutral name is a parameter, `SOURCE_SCHEMA`) with the column names in `manifest.json`.
2. DDL: `docs/data/schema/tcc-schema.sqlserver.sql` (creates `tcc_gold` and `tcc_ops`). The Gold and ops tables here use the same column names as that DDL (`manifest.json` lists the columns the code expects).
3. `ops/run_manifest`, then `gold/*` in any order (rows carry `client_id`, `run_id`, `tax_year`, `method`; `employee_eligibility`/`onezero_matrix`/`employee_period_fact` join on `record_token`).
4. `operational/*` (claims and engagements the engine run recorded). Everything else operational starts empty.

SQLite: `CREATE TABLE` from the column list in `manifest.json` (types are not recorded because SQLite is dynamically typed) and `INSERT` the rows. SQL Server: `bcp`/`BULK INSERT` from the decompressed JSON Lines via `OPENJSON`, e.g. `INSERT tcc_gold.employee_eligibility SELECT * FROM OPENJSON(@json) WITH (...)` with the DDL's types; money columns load into `DECIMAL(18,2)`.

## Gate G2

* Two independent builds of each profile produce identical `manifest.json` (every table's row count and file hash): checked by `seed_export` run twice.
* The seed rows agree with what the harness serves: for every client the API's `eligibility.employees_evaluated` equals `COUNT(DISTINCT record_token)` of `gold/employee_eligibility` for that client, TY2025, `method = 'min_max'` (P1: 107; P2: 202 / 164 / 137 / 125); the API's `scope.clients` and `portfolio.total` equal the account and claim counts. `manifest.json` records the API figures (`api_checks`) and `g2_mismatches: []`.

## Notes

* The values are **not** the certified reference dataset (10,236 / 539 / 656); that is private data and absent. The synthetic parity figures are the committed 81 / 51 / 49.
* Only the data the harness serves is exported; the sealed reference workspace (`/api/workspace/*`) has no hermetic seed (FINDINGS, `COVERAGE.md`).

## Integrity

`manifest.json` lists per table `rows`, `columns`, `content_sha256` (SHA-256 of the decompressed JSON Lines: the identity of the table, identical on every interpreter) and `sha256` (of the committed `.gz`; gzip bytes depend on the zlib build, so verify `content_sha256` after decompressing and use `sha256` only for the file as shipped).
